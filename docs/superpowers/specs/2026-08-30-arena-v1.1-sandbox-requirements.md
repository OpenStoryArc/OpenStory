# Arena v1.1 — sandbox usability requirements

**Date:** 2026-08-30
**Status:** Delivered (v1.1) / Open (future phases)
**Predecessor:** `2026-08-25-arena-sealed-sandboxes-design.md` (v1, PR #115)

## Where these came from

Two sources, both from the first real end-to-end run of Arena on 2026-08-30:

1. **An inside-out audit by the sandbox agent itself.** A Claude Code session
   (`claude-opus-5`) running *inside* a live sandbox probed its own environment and
   wrote a ten-finding capability audit (`ENVIRONMENT.md`) plus an orientation file
   (`CLAUDE.md`), every claim verified by command. This is dogfooding in the truest
   sense: the observed agent producing the spec for its own environment, its reasoning
   captured in that sandbox's OpenStory.
2. **Live UX findings** from operating the stack during that session (budget
   exhaustion behavior, browser-terminal interaction).

## Guiding principle (the reframe that shapes everything below)

**Deliver capability over the internal arena network; never open internet egress.**

The agent verified that `arena-litellm` resolves and serves on the sandbox's internal
network while the public internet is fully blocked (DNS *and* raw-IP both fail). That
means the big v1 gaps — no package installs, no OpenStory read access, no docs — can be
fixed with **internal services** (a registry, an MCP endpoint, a mirror) that the
sandbox reaches the same way it reaches LiteLLM. The zero-egress seal that v1 proved
(and that must still be re-verified under gVisor per the v1 backlog) stays intact.
Every requirement below is written to preserve it.

## Verified environment (baseline, for reference)

Debian 12 (bookworm) aarch64 · 8 cores · 7.7 GB RAM · 814 GB free on `/home/dev` ·
user `dev` (uid 1000) · `/` read-only overlay, `/home/dev` read-write, `/tmp` 64 MB
`noexec` · Node 22 / npm / yarn · git, curl, rg, tmux, openssl present · **no** python,
pip, jq, sqlite3, unzip, editor, gh, ssh, or build toolchain · internal network up,
internet down.

## P0 — a student cannot do real work without these

### R1. Packages must be installable (without opening egress) — OPEN
**What:** Stand up an internal package registry on the arena network (e.g. Verdaccio at
`arena-npm:4873`) and point sandboxes at it (`npm config set registry
http://arena-npm:4873`); pair it with a **writable, exec-capable install target** (see
R3/R4). Optionally pre-bake a warm npm cache / `node_modules` for a course-wide
dependency set.
**Why:** Three independent locks (read-only `/`, no sudo, no egress) currently confine
every project to the Node standard library — "the line between a demo and a usable
workspace" (audit Tier 1.1). A registry on the internal network lifts this while keeping
egress closed.
**Acceptance:** From a fresh sandbox, `npm install express` succeeds and the app runs;
no internet egress is opened (redteam egress probe still fails).

### R2. Ship Python (and decide on a build toolchain) — OPEN
**What:** Add `python3` + `pip` to the image, with pip pointed at an internal PyPI mirror
(or a pre-baked wheel cache) for the same egress-free reason. Decide explicitly whether
`make`/`gcc`/`go`/`rustc` are in scope (needed for native modules / `node-gyp`).
**Why:** Python is "likely the single most-missed tool for this audience" — notebooks,
data work, intro CS curricula (audit Tier 1.2).
**Acceptance:** `python3 -m venv` + `pip install requests` works against the internal
mirror.

### R3. A writable, exec-capable scratch space — DELIVERED (v1.1)
**What:** Provide a larger exec-capable scratch dir under `/home/dev` (e.g.
`/home/dev/.scratch`) and document it; keep `/tmp` as-is or enlarge it exec-capable.
**Why:** `/tmp` is 64 MB and `noexec`, so the routine agent pattern "write a script,
`chmod +x`, run it" is *silently* broken (audit Tier 1.4).
**Acceptance:** Writing and executing a script in the documented scratch dir succeeds.

### R4. `~/.local/bin` on `PATH` — DELIVERED (v1.1)
**What:** Add `~/.local/bin` to `PATH` in `.bashrc` (or the container env).
**Why:** Gives agents somewhere to install user-level tooling while `/` stays read-only.
"Cheapest item on the list" (audit Tier 1.3).
**Acceptance:** A binary dropped in `~/.local/bin` is runnable by name.

### R5. Git identity out of the box — DELIVERED (v1.1)
**What:** Bake a default `user.name` / `user.email` into the image's global git config;
**seed it from `ARENA_USERNAME`** at container start so commits are attributable per
student (`{username} <username@arena.local>`).
**Why:** The first `git commit` fails cold with "Author identity unknown" — every
student hits it, every agent burns a turn on it (audit Tier 1.5). We already thread
`ARENA_USERNAME` into the sandbox, so this is nearly free and closes the loop on
attribution the v1 spec promised.
**Acceptance:** A fresh sandbox can `git commit` with no configuration, authored as the
logged-in username.

### R6. The in-sandbox agent reads OpenStory over MCP — its own history *and* every other harness in the box — DELIVERED (v1.1)
**What:** Ship an **OpenStory MCP server** that the in-sandbox agent connects to (wired
into Claude Code's `.mcp.json` at container start), pointed at the sandbox's own OpenStory
REST API. It must expose **read access to every agent harness observed in that sandbox**,
not just the calling agent's own Claude Code session — so the Claude agent can read what a
pi-mono (or any other) harness in the same box did, and vice versa. That requires the
sandbox's `open-story serve` to watch **all** harness transcript directories (Claude
Code's `~/.claude/projects`, `pi_watch_dir`, and any others), which OpenStory already
supports as a multi-agent observer. Resolve the `localhost:3002` **403** the agent hit
(operator `docker exec` queries succeeded, so reproduce the gate — auth / route / header —
first), and give the MCP a scoped **read-only** credential.
**Why:** OpenStory records rich per-session data across harnesses, but from inside the box
the agent has "no programmatic way to read it back" — it can't ask *"what have I already
tried?"* or *"what did the other harness in this box find?"* Cross-harness read is the
sharper version of the thesis: the box becomes a **shared, legible memory across whatever
agents run in it**, and reading stays observe-never-interfere (query only, never mutate).
"A genuinely novel capability rather than a convenience" (audit Tier 3.8) — the
highest-leverage item for what makes Arena *Arena*.
**Scope / safety:** cross-harness read is bounded to a **single sandbox**, which is a
single user's — so it never crosses the per-user isolation boundary the v1 seal
establishes (topology is the ACL). No sandbox can read another user's OpenStory; the MCP
is reachable only from inside its own box, over the internal network.
**Acceptance:** From inside a sandbox, the Claude agent can, over MCP on the internal
network only: (a) list/query its **own** sessions and events; (b) list/query the sessions
and events of **another agent harness** running in the same sandbox; (c) never mutate any
event (read-only enforced); and (d) cannot reach any other sandbox's OpenStory.

## P1 — high-impact ergonomics and safety

### R7. Core CLI tools in the image — DELIVERED (v1.1)
**What:** Add, ranked by impact here: **`jq`** (this environment is JSON/JSONL to the
core — transcripts, OpenStory events), **`sqlite3`** (there's a live DB at
`/home/dev/data/open-story.db` with no CLI to read it), **`unzip`/`zip`**, an **editor**
(`vim`/`nano` — `git commit` currently has none), `less`, `tree`; consider `gh`/`ssh`
once a git story exists. (audit Tier 2)
**Acceptance:** Each tool present and functional; `git commit` opens an editor.

### R8. Agent orientation shipped in the image — DELIVERED (v1.1)
**What:** Bake a `CLAUDE.md` into the seeded workspace stating the constraints
(read-only root, no egress, what's installed, where OpenStory writes, the internal-network
reframe), and a `settings.json` permission allowlist for routine read-only commands
(`git status`, `ls`, `rg`, `node --version`, …); the `fewer-permission-prompts` skill can
generate it.
**Why:** Every agent otherwise re-derives the same facts (~a dozen tool calls) and some
guess wrong; students face confirmation prompts for safe commands (audit Tier 3.6/3.7).
The agent literally wrote a usable `CLAUDE.md` for us — ship that, refined.
**Acceptance:** A fresh session starts oriented; routine read-only commands don't prompt.

### R9. Fix the README dead end — DELIVERED (v1.1)
**What:** Replace the workspace `README.md`'s "at the -story link" with the real
`https://{username}-story.{base_domain}/` URL (and note the one-time cert/permission
step in dev).
**Why:** It's the first thing every agent reads and it points nowhere; the dashboard's
port is unreachable behind the 403 (audit Tier 3.9). Ties to R6.
**Acceptance:** The README names the actual dashboard URL that works.

### R10. Budget-exhaustion UX + operator top-up — OPEN
**What:** (a) A **soft warning at ~80%** of budget and a **graceful in-terminal message**
at exhaustion ("you've used your $X for this event — ask the organizer to top up"),
instead of the raw LiteLLM 400/429 Claude Code shows today. (b) An **operator top-up
action** in the control plane that raises a key's `max_budget` live via LiteLLM
`/key/update` — verified during this session to work with **no session restart** (budget
is a mutable field on a persistent key). Default to organizer-approved grants for the
classroom case.
**Why:** Live UX finding. Exhaustion currently surfaces as a cryptic API error; the
top-up primitive already exists for free in the architecture — it needs a humane surface.
**Acceptance:** Hitting the cap shows a friendly message; an operator can grant more
without disrupting the running sandbox.

### R11. Browser-terminal interaction — DELIVERED (v1.1)
**What:** Enable tmux `mouse on` by default in the image (hot-applied live this session
and it fixed scrolling), tune ttyd scrollback, and verify Claude Code's TUI scroll/copy
behavior in-browser; document the copy-with-Option tradeoff. Reinforce the split in docs:
**terminal for driving, the `-story` dashboard for reading history** (the good scrollback
experience).
**Why:** Live UX finding — a full-screen TUI wrapped in tmux-in-ttyd swallowed scroll and
cycled history; janky for a first-time student.
**Acceptance:** Mouse-wheel scrolling works out of the box in the browser terminal.

## P2 — depends on use case

### R12. Visual tooling, or remove the dead path — OPEN
**What:** Either add a headless browser (Playwright/Puppeteer) + image tooling
(ImageMagick) if the curriculum needs visual work, **or** remove/disable the installed
`run` skill's browser-driven path that cannot work in a no-egress sandbox.
**Why:** No Puppeteer/Playwright/ImageMagick; the `run` skill advertises a browser path
that dead-ends (audit Tier 3.10).
**Acceptance:** No skill advertises a capability the sandbox can't deliver.

---

## Suggested order (from the agent, adjusted)

1. **R1–R4 (installable packages + writable/exec target + PATH)** — unblocks real work;
   everything else is refinement.
2. **R7 + R2 (jq, sqlite3, Python)** — unblocks routine work.
3. **R5 + R6 + R8/R9 (git identity, OpenStory read access, orientation, README)** — stops
   every agent paying the discovery tax and delivers the read-your-history thesis inside
   the box.
4. **R10 + R11** — the UX polish that makes it classroom-ready.
