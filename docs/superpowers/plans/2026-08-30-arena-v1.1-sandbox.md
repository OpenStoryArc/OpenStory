# Arena v1.1 sandbox — usability + in-box OpenStory MCP · Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make an Arena sandbox pleasant for real work and give the in-box agent read access to OpenStory over MCP — its own history and every other harness in the same box — without opening internet egress.

**Architecture:** All changes are to the existing self-contained `arena/` package (branch `feat/arena-v1.1`, stacked on `feat/arena-v1`). Most work is the sandbox **image** (`arena/sandbox/Dockerfile`, `welcome.sh`, new `tmux.conf`, seeded `/opt/workspace` files) plus a second binary (`open-story-mcp`) built from the same Rust workspace and wired into the sandbox's Claude Code via `.mcp.json`. Everything the box needs is delivered on `localhost`/the internal network; the zero-egress + gVisor seal from v1 is preserved. Tests extend the existing `arena/sandbox/smoke.sh` harness and the DockerDriver ignored integration test.

**Tech Stack:** Docker (multi-stage, `node:22-bookworm-slim` runtime), bash, tmux, Debian apt, the Rust workspace's `open-story-cli` + `open-story-mcp` binaries, Claude Code `.mcp.json` / `settings.json`.

**Spec:** `docs/superpowers/specs/2026-08-30-arena-v1.1-sandbox-requirements.md`

### Task 4: Build + ship `open-story-mcp`; root-cause the localhost:3002 403 (R6, part 1)

**Files:**
- Modify: `arena/sandbox/Dockerfile` (build + copy `open-story-mcp`), `arena/sandbox/smoke.sh`

**Interfaces:**
- Produces: `/usr/local/bin/open-story-mcp` in the image; the OpenStory REST read endpoints the MCP uses reachable at `http://localhost:3002` from inside the box (as user `dev`), returning 200.

- [ ] **Step 1: Reproduce and root-cause the 403 first (investigation).**

The v1.1 audit reported `localhost:3002` returning **403** from inside the box, while operator `docker exec` queries succeeded. The server's `auth.rs` returns 403 from principal/role middleware (`require_role` → 403 when `local_principal_id` empty / no role) and from the admin-token tier check — not from `api_token` alone (that's 401). Run the actual sandbox and find which routes the MCP needs and which return 403:

```bash
docker exec "$C" sh -c 'for p in /api/sessions "/api/sessions/$(curl -s localhost:3002/api/sessions | jq -r .sessions[0].session_id)/records" /api/search?q=x; do
  echo "$p -> $(curl -s -o /dev/null -w %{http_code} "localhost:3002$p")"; done'
```

Record which return 200 vs 403. Decide the minimal fix that keeps the seal:
- If only admin/principal-gated routes 403 and the MCP's read tools use ungated routes → no server change needed; proceed.
- If a read route the MCP needs is gated → either configure the sandbox's open-story with an `api_token` and give the MCP that token via `OPENSTORY_API_URL` + auth env, **or** seed a `[person]`/principal with a read role at boot. Prefer the token: set `OPEN_STORY_API_TOKEN` in `welcome.sh` (a value generated per-container, kept on localhost only) and pass it to the MCP. Document the choice in the report.

- [ ] **Step 2: Build the MCP binary in the image.**

In the `oss-build` stage, build both binaries:

```dockerfile

```

And copy it into the runtime stage next to `open-story`:

```dockerfile
COPY --from=oss-build /src/rs/target/release/open-story-mcp /usr/local/bin/open-story-mcp
```
