## Verdict

- **Realistic operating range (1x–10x, ≤1200bpm / ≤20 interactions/sec): ALL NFRs MET ✅.** At 1x/10x, interaction p95 is single-digit-to-low-double-digit ms — well under the 50ms bar.
- **100x is a pathological burst** — 128 interactions fired simultaneously (~200/sec), ~10× beyond any human or the replay driver. Treat its numbers as the CEILING, not the operating point.
- **The one knee at 100x is `interaction` p95.** Root cause: `post_interaction` does a synchronous SQLite `insert_event` on the response path; the control primitives (broadcast-only, no DB write) all hold ~45ms p95 at the same burst. That write is the delta.
- **Fix path (only if a real workload ever approaches this):** move the interaction `insert_event` off the response path — a single-consumer mpsc writer task (FIFO, preserves order) draining to SQLite, with `ui-state` served from an in-memory `tokio::watch` updated synchronously. NOT built yet (YAGNI — no real load reaches the knee); the door is documented.

## Notes

- `delivered`/dropped-broadcast measurement needs a connected WS sink (a browser or a node WS client counting received vs `delivered`); not measured here — tracked for a follow-up.
- 1x spaces beats 500ms apart (no concurrency → true baseline latency); 10x overlaps; 100x is a fire-at-once burst (max contention). 16 warmup beats discarded per tempo. Release build, UI not driven.
