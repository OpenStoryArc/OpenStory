# Introspection scripts — problem space, data, methodology

A reference for the five deterministic scripts in `scripts/` that answer
team-monitoring questions over the OpenStory event store, plus the test
runner that exercises them. This document frames *why* the scripts are
shaped the way they are and *how* far the determinism actually goes.

For runnable cases against live data, see `cases.md` (auto-generated by
`scripts/build_cases_report.py`).

## 1. The problem space

Every question a team has about a coding-agent session reduces to a
traversal of the same graph:

```
   intentions ←──────────────────────────────────→ outcomes
   ─────────                                       ────────
   user prompts                                    file writes
   plans                                           commits
   skill invokes                                   PRs
   knowledge consults                              state changes
                                                   tool results

         ──── metadata layers ────
         user · host · principal_id · project · branch · skill · time
```

A question picks a node-class on one side and asks for a path back to the
other side, often filtered by a metadata layer:

| Customer question | Traversal |
|---|---|
| Why this PR? | outcome (PR) → walk backwards to all owning intentions |
| Trail of prompting? | intentions over time, classified by shape |
| Why this state? | outcome (file write) → walk backwards to owning intention |
| What knowledge / skills? | which auxiliary tools attached to the intentions |
| How is the team consuming the agent? | aggregate over the metadata layer |
| Personal vs work? | filter the metadata layer (host × project × principal) |

The five scripts in `scripts/` each pin one traversal. They are not new
data — they are deterministic projections of the existing event stream.

## 2. What's available in the data

### Atoms (raw, written by the listener)
CloudEvents 1.0, persisted in SQLite + JSONL backup. Subtypes:

- `message.user.prompt` — human prompts
- `message.user.tool_result` — tool outputs returned to the agent
- `message.assistant.text` / `.tool_use` / `.thinking` — agent output
- `system.turn.complete` — turn boundaries
- `system.session_start` · `system.error` · `system.compact` · `system.hook`

Each event carries: `id`, `seq`, `session_id`, `timestamp`, `is_sidechain`,
`record_type`, `payload`, `depth`, `parent_uuid`, `truncated`,
`payload_bytes`. Plus the identity layer added in PR #54: `person_id`
and `principal_id` on every newly ingested event.

### Sessions (groupings)
`/api/sessions` returns 488 rows in the live store, each with:
`session_id`, `status`, `start_time`, `last_event`, `event_count`,
`project_id`, `project_name`, `label`, `branch`, `total_input_tokens`,
`total_output_tokens`, `host`, `user`, `person_id`, `principal_id`.

Note: `/api/sessions/{id}/summary` does **not** carry `host`, `user`, or
`branch` — those live only on the list endpoint. The five scripts join
through the list when they need attribution.

### Patterns (derived, written by the patterns consumer)
Per-session pattern records with their own metadata. Most useful types:

- `turn.sentence` — one record per turn, with `metadata.verb`, `subject`,
  `object`, `human.content` (the prompt), `eval.content` (the response),
  `subordinates` (preparatory tool calls)
- `turn.phase` — phase classification per turn
- `eval_apply.eval` / `eval_apply.apply` — eval-apply cycle markers
- `error.recovery` · `test.cycle` · `git.workflow`

Pattern coverage is partial: only **139 of 488 sessions** (28%) currently
have any `turn.sentence` records. The rest are either too short, too
recent, or pre-detector. This is the headline limit on
`prompt_trail.py`'s reach.

### Search
SQLite FTS5 over event payloads, exposed as `/api/search?q=...&limit=N`.
Returns `(event_id, session_id, record_type, snippet, rank)`. The cap is
real — large queries truncate at the limit, which is what produced the
manual undercount we surfaced earlier in this conversation.

### What is *not* in the data (yet)
The five scripts derive these, but none is materialized as a first-class
table:

- **PRs** — derived from `tool_call.payload.input.command ~ "gh pr create"`
- **Commits** — derived from `git commit -m ...` or HEREDOC form
- **Skills** — derived from `user_message ~ "Base directory for this skill: …"`
- **Knowledge consultation** — derived from `Read` of `*.md` outside excludes
- **OpenStory introspection tier** — derived from the 5 signatures in
  `openstory_tier_usage.py`
- **Reverse provenance from file path → owning prompt** — computed per
  query, not indexed

Every one of these is a candidate for a small projection consumer. The
scripts are the spec.

### Known data gaps
- **Subagent record attribution** — `/api/sessions/{id}/records` returns
  records whose `session_id` field disagrees with the URL path for at
  least 2 subagent sessions. See `docs/BACKLOG.md` ("Subagent record
  attribution") for the spec to resolve.
- **Principal coverage** — 270/488 sessions (55%) carry a `principal_id`;
  the rest predate the resolver or run on un-enrolled hosts.
- **`/summary` field gaps** — host/user/branch missing; consumers must
  join through `/api/sessions`.

## 3. Methodology

The pipeline that produced each script:

```
┌─────────┐    ┌────────────┐    ┌──────────────┐    ┌──────────┐
│question │ →  │ atom in    │ →  │ pure derived │ →  │ tested at │
│         │    │ event      │    │ function     │    │ 3 layers │
│         │    │ stream     │    │              │    │          │
└─────────┘    └────────────┘    └──────────────┘    └──────────┘
```

Concretely, for each script:

1. **Pick the question.**
2. **Identify the nearest deterministic atom.** "PR created" =
   `tool_call.command ~ /gh\s+pr\s+create/`. "Skill invoked" =
   `user_message ~ /Base directory for this skill:/`. The atom is what
   makes the answer reproducible — anything fuzzier is a heuristic.
3. **Define the derivation.** Specify exactly how other atoms in the
   session relate to the answer: e.g., a PR's prompt trail is the union
   of `turn.sentence` patterns whose `started_at` falls within the
   session, ordered by `metadata.turn`.
4. **Implement as a pure function** taking parsed events to a typed
   result. No I/O at the core — I/O lives at the edges (`fetch()` and
   `main()`).
5. **Test at three layers**:
   - **A. Unit fixtures** (`<script>.py --test`): pure function vs.
     hand-built event lists. 100% deterministic, no API.
   - **B. Anchor scenarios**
     (`test_introspection_scenarios.py --anchors`): pin five sessions
     across archetypes, assert *bounded* properties (e.g., "explain
     share ≥ 0.30") rather than exact values, so detector wobble doesn't
     false-fail. 100% deterministic on completed sessions when detectors
     are stable.
   - **C. Corpus invariants** (`--invariants`): properties that must
     hold over all sessions, regardless of which sessions are present.
     Concrete examples currently checked:
     - archetype ∈ {socratic, directive, plumbing, recovery, mixed}
     - write+explain+check shares ∈ [0, 1]
     - PR events from session S all carry session_id == S
     The third invariant is the one that surfaced the subagent attribution
     anomaly. Tests as a discovery mechanism, not just a regression net.

### Determinism ceiling

| Layer | Ceiling | What it catches |
|---|---|---|
| A — unit fixtures | 100%, instant, no I/O | classifier regressions, parsing |
| B — anchor scenarios | 100% on completed sessions assuming stable detectors | API drift, schema changes, real regressions |
| C — corpus invariants | 100% on **properties** (specific answers drift as new sessions land) | edge cases at scale, contract violations |
| Snapshot/golden (not yet built) | byte-exact, brittle by design | "this session's output changed" — useful when you *want* drift to be loud |

The wildcard is detector evolution. When `turn.sentence`'s verb taxonomy
expands (or a new pattern type ships), anchor outputs *should* shift —
and these tests will tell you which sessions moved. That's a feature, not
a flake.

## 4. The five scripts at a glance

| Script | Question | Reads | Returns |
|---|---|---|---|
| `why_this_pr.py` | Why was this PR needed? | records, sentences, sessions list | `WhyPr[]` (PR title, prompt trail, plans, commits) |
| `prompt_trail.py` | What's the shape of the prompting? | sentences | `TrailShape` (verb mix → archetype) |
| `state_provenance.py` | Why does this file look like this? | search, records, sentences | `Provenance[]` (turn, prompts, count) |
| `skills_used.py` | What skills + knowledge did the agent consult? | records, sessions list | `SkillsUsed` (invokes, reads, knowledge) |
| `openstory_tier_usage.py` | How was OpenStory itself used? | records, sessions list | `TierUsage` (rawdog/rest/script/skill/mcp counts) |

Each is REST-only (no raw file grep), importable as a module, has a
`--test` flag, and lives behind a thin CLI. Together with
`test_introspection_scenarios.py` they form a self-documenting test of
both the data and the consumers built on top of it.

## 5. Headline corpus findings

Computed live; full numbers in `cases.md`.

- **Tier mix is REST + MCP-dominant.** 80 sessions hit `/api/*`, 48 hit
  `mcp__openstory__*`, 25 ran a script, 17 used the rawdog anti-pattern
  anyway, 9 used the skill layer. 116 of 488 sessions (24%) touched
  introspection at any tier.
- **Most coding sessions don't fit neat archetypes.** 48.9% land as
  "mixed", 20.9% directive, 11.5% plumbing, 11.5% socratic, 7.2%
  recovery. The classifier exposes the boundary cases honestly rather
  than overfitting.
- **Personal vs work is a `watch_dir_pattern` problem.** Engineer A alone shows
  up across 18 distinct projects on the same host/user pair. The fleet
  resolver already handles this — needs additional principals enrolled.
- **The team-day skill is co-used.** 6 invocations of `/team-day`, split
  3/3 between Engineer A and Engineer B — the strongest team-shared-tool signal in
  the data.
- **Subagent attribution is unresolved.** Two `agent-…` sessions have
  records that disagree with their parent's `session_id`. Filed as
  follow-up.

## 6. Operating principle — 90% deterministic, 10% narrative overlay

Every introspection skill in this stack should be roughly **90%
deterministic** (queries, scripts, code, structured data) and **10%
narrative overlay** (a thin synthesis layer on top — hand-written
hypotheses, archetype labels, the cross-cutting findings paragraph).

Concretely in this repo:

| Layer | Built from | Determinism | Role |
|---|---|---|---|
| The five scripts | Pure Python, REST-only, fixtures + `--test` | 100% reproducible | the answer |
| Anchor scenarios | Pinned session ids, bounded assertions | 100% on completed sessions | the regression net |
| Corpus invariants | Properties over all sessions | 100% on properties | the discovery net |
| `cases.md` | Curated cases run against live data | 100% reproducible per data snapshot | the illustration |
| `cases.md` hypotheses | Hand-written one-liners per case | author-provided | **the 10% — a frame the reader can compare reality against** |
| Cross-cutting findings | Synthesis paragraph in `cases.md` | author-provided | **the 10% — what the data is *saying*** |

The 10% is where the model (or human) earns its keep — naming archetypes,
proposing what a case demonstrates, noticing patterns across cases. The
90% makes that synthesis falsifiable: every claim is anchored to a
specific session id or path, every number reproducible by re-running.

This is why the cases file pairs a *hypothesis* with each pinned id.
When the data drifts, the hypothesis either still holds (boring, good)
or is now wrong (interesting, also good — update the hypothesis or
investigate the data). Either way the deterministic floor catches the
shift; the narrative layer is the part that can productively be
revisited.

## 7. Reproducing this report

```bash
# rebuild the cases appendix from current data
python3 scripts/build_cases_report.py > docs/research/introspection-scripts/cases.md

# verify the scripts haven't regressed
for s in why_this_pr prompt_trail state_provenance skills_used openstory_tier_usage; do
  python3 scripts/${s}.py --test
done

# verify against the corpus
python3 scripts/test_introspection_scenarios.py
```

The whole pipeline runs in well under two minutes and is fully reproducible
from a clean checkout (assuming the local server has the same data).
